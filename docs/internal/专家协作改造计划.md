# 专家协作功能说明与改造计划

## 文档目的

本文说明本项目“专家往来 / 专家信件”功能原本解决什么问题、当前实现为什么不能继续修补，以及如何在保留真实专家委派能力的前提下，将其改造成可信、可追踪、对用户真正有价值的协作与核验功能。

本项目的长期定位是可扩展的本机教育助手工作台，目前只落地了申学方向。因此，本次设计先服务于项目调研、资料核验、申请策略、文书写作和文书审校，不为了未来可能出现的其他教育方向提前建设通用分布式 Agent 网络。

## 实施状态

本专题改造已经落地；总里程碑、验证证据与提交纪律以 [IMPLEMENTATION_PROGRESS.md](./IMPLEMENTATION_PROGRESS.md) 为唯一状态来源。本文前半部分保留旧 Mailbox 的问题分析，后半部分作为可信协作的设计与验收依据。

当前实现包括持久化 task/handoff、结构化 `submit_specialist_result`、第二次真实 Child Query、统一 InputFileManifest、消息级 Web 面板和飞书摘要。Child Query 由 `SpecialistGateway` 边界统一启动，本地实现为 `LocalClaudeSpecialistGateway`。旧 `agent_mailbox` 表仅为数据库兼容保留，运行时、API、Web 和飞书均已停止读写和展示。没有有效 HTTP(S) 来源的“verified” finding 会降级为 unresolved；服务重启或用户停止时，未完成 task/handoff 进入 interrupted。

---

## 决策摘要

- 删除当前 `AgentMailbox` 的产品语义，不继续完善“专家信件”。
- 保留现有真实专家委派、流式执行、并发控制、工具权限和工作区隔离能力。
- 新建以真实执行为基础的“协作任务、交接、核验结果”模型。
- 专家之间不进行不受控的自由聊天；主助手负责协调专家任务和后续复核。
- 用户看到的是最终答案，以及绑定在这条答案上的结构化“协作与核验记录”。
- 飞书继续只使用一个主机器人，不为每个专家单独创建机器人。
- 当前不接入 A2A 协议，但内部接口保持 A2A-ready，未来可以增加远程 Agent 适配器。
- 用户上传文件统一形成经过校验的附件清单，并自动传给主助手及实际处理文件的协作助手，不能依赖主助手记得转述路径。

一句话结论：

> 保留真实委派，删除伪信件；把“专家表演”改造成会实际改变答案的协作与核验。

---

## 这个功能应该是什么

“专家协作”不是让多个 Agent 在界面里模拟社交聊天，而是让主助手在一轮任务中，把有明确边界的工作交给不同的专业角色处理，再根据他们的真实结果完成复核、冲突处理和最终综合。

以申学项目调研为例：

```text
用户：核对 NUS MSc CS 的截止日期、轮次和国际生要求
  ↓
主助手拆解任务
  ├─ 项目研究员：查找项目与研究生院官方页面
  └─ 资料核验员：复核截止日期、轮次和页面时效
  ↓
主助手处理冲突和未确认项
  ↓
输出最终答案
  ↓
在同一条答案下附带协作与核验记录
```

该功能的用户价值是：

- 复杂任务可以由多个专业角色并行或串行完成；
- 关键事实经过独立复核；
- 用户能知道哪些结论已确认、存在冲突或仍无法确认；
- 每个重要结论可以追溯到来源和负责角色；
- 用户不需要阅读内部工具日志或模型推理。

## 之前的实现是什么样的

### 已经真实工作的部分

项目已经具备真实的专家委派执行器，主要位于：

- `apps/server/src/runtime.ts`
- `apps/server/src/agent-profiles.ts`
- `apps/server/src/orchestrator.ts`

主助手可以调用受管委派工具，启动独立的 Child Query。专家拥有自己的：

- system prompt；
- Skills 白名单；
- MCP 服务白名单；
- 工具权限；
- 最大 turns；
- high effort；
- 工作区保护；
- 并发槽；
- 流式活动事件。

这些专家会真实运行，并将输出返回主助手。这一部分有明确价值，应当保留。

### “专家信件”的实现

原功能额外提供了：

- `mailbox_post`；
- `mailbox_reply`；
- `AgentMailbox` SQLite 存储；
- 网页“专家往来”列表；
- 飞书成稿末尾的“专家往来”摘要；
- “代理信件”活动块。

其实际流程是：

```text
主助手或专家调用 mailbox_post
  ↓
向 agent_mailbox 表插入一行文本
  ↓
生成一条供前端展示的活动事件
  ↓
网页或飞书显示这封信
```

但收件专家不会收到这段内容，也不会继续执行。`mailbox_reply` 与 `mailbox_post` 的行为相同，没有真正的回复线程、目标会话或任务状态。

因此，它本质上是一个带收发件人标签的日志系统，而不是 Agent 通信系统。

## 为什么必须改

### 1. 产品承诺与实际行为相反

界面称其为“专家往来”和“信件”，用户自然会认为收件专家看到了消息并作出了回应。实际实现只保存和展示文本。

### 2. 它可能降低答案质量

运行时提示要求主助手在需要专家第二轮处理时使用 `mailbox_post / mailbox_reply`。但写信不会再次启动专家，模型可能用一封无效信件代替真正的复核。

### 3. `post` 和 `reply` 没有语义区别

当前没有：

- `replyTo`；
- 对话线程；
- 待处理状态；
- 已读状态；
- 已回答状态；
- 收件人消费；
- 对最终答案的影响关系。

### 4. 展示位置错误

网页按 conversation 聚合所有信件，并统一显示在消息列表顶部，而不是绑定到产生它们的具体 Agent 回复。对话变长后，旧信件会逐渐脱离上下文。

### 5. 飞书成稿会被内部过程污染

当前飞书会把最近的信件摘要直接拼到最终回答中。它可能重复正文、暴露内部措辞，或让用户误以为真人专家参与了处理。

### 6. “专家”称呼容易误导

这些角色是应用内的协作助手，不是外部真人专家。产品可以保留“项目研究员”“资料核验员”等明确角色名称，但不应暗示发生了真实的人际通信。

### 7. 缺少因果验证

现有测试只证明信件可以写入数据库和显示，没有证明：

- 收件专家获得了消息；
- 收件专家采取了行动；
- 产生了第二次真实执行；
- 新结果进入了主助手上下文；
- 最终答案因此发生改变。

---

## 为什么不继续在原实现上修补

若要把 Mailbox 修成真正的 Agent 消息系统，需要重新增加：

- 活跃专家会话；
- 消息投递；
- 会话恢复；
- 收件确认；
- 异步任务状态；
- 专家生命周期；
- 失败与超时；
- 防止循环通信；
- 跨 Agent 权限控制。

这相当于在错误抽象上重新建设一套编排器，而项目已经拥有主助手和真实委派执行器。更简单可靠的做法是：由主助手继续担任编排者，把每次专家交接转换成真实的新任务。

因此，本次不是推倒整个专家系统，而是：

```text
保留：专家定义 + 真实委派 + 流式活动 + 权限隔离
删除：伪 Mailbox + 伪信件 UI + 飞书信件摘要
新增：协作任务 + 真实交接 + 结构化核验结果
```

## 目标产品形态

### 用户默认看到的内容

最终答案仍然是视觉主体：

```text
最终回答正文……

协作与核验 · 2 位协作助手
3 项已核验 · 1 项存在冲突 · 4 个官方来源
```

### 用户展开后看到的内容

```text
项目研究员
任务：查找 NUS MSc CS 的截止日期与轮次
状态：已完成
结论：项目页列出 12 月 1 日

项目研究员 → 资料核验员
交接：复核国际生是否存在单独 Round

资料核验员
状态：已完成
结论：官方页面没有明确区分国际生 Round
核验状态：无法确认
```

### 不向用户展示的内容

- chain-of-thought；
- 私密 reasoning；
- 完整工具输入输出；
- Bash、文件路径和原始 API 响应；
- 专家之间的寒暄和重复内容；
- 没有改变任务结果的内部消息。

### 没有实际协作时

如果主助手直接完成任务，不显示任何协作模块。

## 协作原则

### 主助手负责协调

专家不能继续嵌套委派。专家可以在结构化结果里建议下一步需要哪位协作助手复核，但是否执行由主助手决定。

### 每次展示都必须对应真实执行

只有在目标专家实际启动后，才创建可见交接记录。不存在“发出但无人处理”的信件。

### 交接传递结构化结果

后一位专家获得的是：

- 原任务；
- 前一位专家的结果摘要；
- 已发现的事实与来源；
- 未解决问题；
- 本次复核要求。

### 最终答案由主助手负责

专家结果是输入，不直接代替最终回答。主助手负责处理冲突、标注不确定性并面向用户表达。

## 数据模型

保持模型尽量小，不提前建设通用 Agent 网络。

### `collaboration_tasks`

记录每次真实专家执行：

```ts
interface CollaborationTask {
  id: string
  runId: string
  assistantMessageId: string

  specialistId: string
  displayName: string
  sourceTaskId: string | null

  status:
    | 'queued'
    | 'running'
    | 'completed'
    | 'failed'
    | 'interrupted'

  requestSummary: string
  resultSummary: string | null
  result: SpecialistResult | null

  createdAt: number
  startedAt: number | null
  completedAt: number | null
}
```

### `collaboration_handoffs`

记录已经产生真实目标任务的交接：

```ts
interface CollaborationHandoff {
  id: string
  runId: string
  sourceTaskId: string
  targetTaskId: string
  question: string
  status: 'running' | 'completed' | 'failed'
}
```

### `SpecialistResult`

```ts
interface SpecialistResult {
  summary: string

  findings: Array<{
    claim: string
    status: 'verified' | 'conflicting' | 'unresolved'
    sourceUrls: string[]
    verifiedAt?: string
  }>

  openQuestions: string[]

  recommendedFollowups: Array<{
    specialistId: string
    question: string
  }>
}
```

结构化结果只记录适合用户查看和供主助手使用的信息，不记录完整推理。

## 真实专家执行与交接

### 专家任务生命周期

```text
主助手调用 delegate_* 工具
  ↓
创建 collaboration_task: queued
  ↓
获得并发槽
  ↓
状态变为 running
  ↓
启动真实 Child Query
  ↓
保存结构化结果
  ↓
completed / failed / interrupted
  ↓
结果返回主助手
```

### 专家提交结构化结果

向专家提供受控工具：

```text
submit_specialist_result
```

参数包含：

- `summary`；
- `findings`；
- `openQuestions`；
- `recommendedFollowups`。

如果专家没有调用该工具：

- 使用最终文本生成 `resultSummary`；
- 标记为非结构化结果；
- 不推断或伪造核验状态、来源和结论。

### 真实 follow-up

扩展现有专家委派输入：

```ts
{
  task: string
  context?: string
  desiredOutput?: string
  sourceTaskId?: string
}
```

当存在 `sourceTaskId` 时：

1. 验证源任务属于当前 run；
2. 读取源专家的结构化结果；
3. 把源结果和新问题传给目标专家；
4. 创建新的真实专家任务；
5. 创建 handoff；
6. 等待目标专家执行完成；
7. 将结果返回主助手。

专家之间看起来发生了交接，但底层仍由主助手和宿主编排器控制，不允许不受控的 Agent 循环。

## 与消息和分支的绑定

协作记录必须绑定具体的 `assistantMessageId` 和 `runId`，不能继续挂在整个 conversation 顶部。

```ts
interface MessageDto {
  // existing fields

  collaboration?: {
    tasks: CollaborationTaskDto[]
    handoffs: CollaborationHandoffDto[]
    summary: CollaborationSummaryDto
  }
}
```

由此保证：

- 每条回答只显示本轮协作；
- Retry 会产生新的协作记录；
- 编辑旧消息不会把新专家结果挂到旧回答；
- 被替换分支的协作记录不会污染当前分支；
- 回放重新运行专家任务，不伪装成原任务继续执行。

## 为什么不采用“每个专家一个飞书机器人”

不建议把飞书群作为 Agent 内部通信总线。

主要原因：

- 飞书机器人接收事件主要面向用户发给机器人或用户在群中 @ 机器人的消息；
- 机器人不能像普通用户一样可靠地通过互相 @ 形成自然对话；
- 即使由中央服务使用多个 App 凭据分别发消息，真正的编排仍发生在后端，飞书群只是展示层；
- 每个专家需要独立 App ID、Secret、权限、版本发布和运维；
- 容易产生循环回复、重复消息和群聊噪音；
- 记忆、附件、会话和用户身份归属会变复杂；
- 增加专家角色时必须继续创建飞书应用。

飞书官方机器人接入说明可参考：[应用配置说明](https://open.feishu.cn/document/develop-an-echo-bot/faq)。

未来若用户确实希望直接访问不同角色，可以把多个机器人作为不同入口，例如“项目调研助手”和“文书教练”。它们仍应连接统一后端和数据层，不依赖机器人之间通过飞书聊天完成协作。

---

## 是否采用 A2A

当前不采用 A2A 协议。

A2A 主要用于不同厂商、不同框架、不同服务器或不同组织拥有的独立 Agent 系统之间进行能力发现、任务管理和互操作。当前专家都运行在同一个代码库、进程、工作区、数据库和编排器内，引入完整 A2A 会增加：

- Agent Card；
- JSON-RPC / HTTP 服务；
- 跨服务鉴权；
- 网络重试和幂等；
- SSE 或 Push Notification；
- 分布式任务状态；
- 独立部署和故障恢复。

这些复杂度目前没有对应的用户价值。

A2A 官方说明可参考：[A2A 项目](https://github.com/a2aproject/A2A) 和 [A2A Specification](https://github.com/a2aproject/A2A/blob/main/docs/specification.md)。

### 保持 A2A-ready

定义内部专家边界：

```ts
interface SpecialistGateway {
  describe(): SpecialistDescriptor

  run(
    task: CollaborationTaskInput
  ): AsyncIterable<CollaborationEvent>
}
```

当前实现：

```text
LocalClaudeSpecialistGateway
```

未来出现独立远程专家时，可以新增：

```text
A2ASpecialistGateway
```

业务层、数据模型和 UI 不需要随之重写。

### 何时再评估 A2A

满足以下一项或多项时再考虑：

- 专家由不同团队独立开发和部署；
- 接入外部教育机构或第三方 Agent；
- 专家拥有独立权限、计费或数据隔离；
- 任务需要跨服务运行较长时间；
- 专家需要独立扩缩容和故障恢复；
- 需要第三方通过标准协议发现并调用本项目专家。

## 上传附件可靠性与专家文件发现

专家协作要可信，前提是主助手和协作助手能稳定定位用户上传的输入文件。当前“本轮新上传文件由主助手立即处理”的链路已经有精确路径提示，但还不能保证所有场景都不会找不到或找错文件。

### 当前已经具备的保障

网页和飞书上传成功后，文件会写入当前会话工作区：

```text
data/workspaces/<conversationId>/attachments/<storedName>
```

附件记录会保存：

- 原始文件名；
- 唯一存储名；
- MIME 类型；
- 文件大小；
- SHA-256；
- 工作区相对路径；
- 所属 conversation；
- 绑定的用户消息。

当本轮主助手收到 PDF、Word、Excel、Markdown 等非图片附件时，运行时会把原始文件名和精确相对路径写入提示词：

```text
resume.pdf → attachments/resume-a13f6c21.pdf
```

并要求主助手直接读取该路径，不要按原始文件名重新搜索。重名文件会自动生成唯一存储名。图片会以内嵌图像形式发送给主助手。飞书附件如果下载、权限或格式校验失败，也会向用户显示明确提示。

因此，以下场景风险较低：

- 用户本轮上传一个支持的文档并立即让主助手读取；
- 用户本轮上传图片并让主助手直接看图；
- 带附件的消息正常排队后开始运行；
- 同一会话内 Retry 或普通编辑分支继续使用原消息附件。

### 仍然存在的风险

| 场景 | 当前风险 | 原因 |
| --- | --- | --- |
| 本轮新上传文档，主助手处理 | 较低 | 主助手提示中包含精确路径 |
| 本轮上传图片，主助手看图 | 较低 | 图片以内嵌内容传入，但缺少路径清单 |
| 主助手把文件任务交给协作助手 | 中高 | Child Query 不会自动获得附件清单 |
| 后续一轮说“继续处理之前的文件” | 中等 | 当前轮只注入当前消息附件 |
| 新建分支对话后继续处理文件 | 高 | 新 conversation 不复制附件绑定和文件 |
| 回放任务中的输入附件 | 中等 | 工作区可能恢复，但本轮提示未必恢复附件清单 |
| 数据库存在附件记录但磁盘文件缺失 | 高 | 运行前没有统一完整性检查 |

### 问题一：协作助手不会自动获得附件清单

当前协作助手只收到：

```text
<delegated_task>
...
</delegated_task>

<context_from_main_agent>
...
</context_from_main_agent>
```

它与主助手共用同一个 workspace，但不会自动获得本轮附件的文件名、路径和类型。主助手必须主动把准确路径写进委派参数。

这对文书场景尤其危险：

- 文书写作和文书审校只有 `Read / Write / Edit`；
- 它们没有 `Glob` 或 Bash 文件搜索能力；
- 如果主助手只说“审校用户上传的简历”，协作助手不知道应该读取哪个文件；
- 多个简历或 SOP 版本同时存在时，即使搜索成功也可能选错。

目标行为应改为：宿主自动把附件清单注入专家任务，不依赖主助手转述。

### 问题二：图片没有进入路径清单

图片目前会以 base64 内嵌给主助手，但附件提示会过滤图片，因此主助手可能看得到图片，却不知道原文件位于：

```text
attachments/photo.png
```

当任务需要把图片交给协作助手、调用文件工具、转换格式或复制原图时，仍可能找不到目标路径。

目标行为应是：图片既以内嵌形式提供，也出现在统一附件清单中。

### 问题三：历史附件不会自动进入后续轮次

用户下一轮说：

> 继续修改我刚才上传的简历。

如果没有再次附加文件，当前运行的附件列表为空。系统只能依赖：

- Claude Session 仍记得上一轮路径；
- 主助手主动使用 `Glob` 搜索；
- 工作区内没有多个同类文件；
- 分支或恢复没有改变 Session。

当前 `workspace_files` MCP 只管理已交付货架文件，不提供用户上传输入文件清单。

目标行为应是提供只读 `list_input_files`，并让系统根据来源消息、文件类型和文件名定位历史附件。有多个合理候选时必须让用户选择，不能由模型猜测版本。

### 问题四：新对话分支不会复制附件

同一 conversation 内创建编辑或 Retry 分支时，可以继续引用原附件记录。但当 `asNewConversation: true` 时，消息文本会被克隆，附件绑定不会复制到新 conversation，新工作区也没有可靠的文件副本。

目标行为应在新对话分支时：

1. 找出分支可见历史中被引用的用户附件；
2. 把文件复制到新 conversation 的 `attachments/`；
3. 创建属于新 conversation 的附件记录；
4. 绑定克隆后的对应消息；
5. 对缺失文件显示明确错误或跳过说明。

不能直接复用旧附件 ID，因为附件和工作区都属于原 conversation。

### 问题五：缺少运行前文件完整性校验

附件数据库状态为 `ready`，不代表文件仍然存在。文件可能因为手工清理、异常恢复、快照问题或磁盘错误而缺失。

目前：

- 图片在构造 SDK 消息时直接读取，缺失可能导致整轮失败；
- 文档只把路径告诉 Agent，Agent 调用 `Read` 时才发现不存在；
- 用户无法在执行开始前知道具体哪个文件失效。

目标行为是在 Run 开始前统一校验：

- 附件属于当前 conversation；
- 数据库状态为 `ready`；
- 相对路径位于当前 workspace；
- 磁盘文件存在且为普通文件；
- 实际大小与记录一致；
- 必要时校验 SHA-256；
- 失败时明确指出文件名和失败原因。

校验失败时不允许模型凭空猜测文件内容。

### 问题六：运行中补充消息的附件作用域

正常新 Run 会先把附件绑定到用户消息，再从消息读取实际绑定成功的附件。运行中的 supplement 当前会先按附件 ID 读取记录，再创建消息；这一步没有先按 conversation 收紧。

如果传入其他 conversation 的附件 ID：

- 数据库不会把它绑定到当前消息；
- 但错误的附件元数据仍可能进入当前 RuntimeInputQueue；
- Agent 可能读取不到路径，或误读当前工作区中的同名文件。

目标行为是新增按会话过滤的查询：

```ts
getConversationAttachments(
  conversationId: string,
  attachmentIds: string[]
): StoredAttachment[]
```

Supplement 必须使用消息创建后实际绑定成功的附件列表，不能直接信任请求中的 ID。

### 问题七：回放没有稳定恢复输入附件语义

回放会恢复工作区快照，但若新 Run 没有绑定原用户附件，提示词不会自动列出输入文件。模型可能看到文件存在，却不知道哪些是本轮用户输入、哪些是中间产物。

目标行为是把经过验证的附件 manifest 作为回放快照的一部分：

- 保存原附件文件名、相对路径、MIME、大小和 SHA-256；
- 恢复工作区后重新校验；
- 回放输入自动注入同一份 manifest；
- 找不到快照文件时明确终止对照，而不是静默忽略。

## 统一附件 Manifest

新增运行时附件清单，作为用户输入文件的唯一真相源：

```ts
interface InputFileManifestItem {
  attachmentId: string
  conversationId: string
  sourceMessageId: string

  originalFileName: string
  relativePath: string
  mimeType: string
  size: number
  sha256: string

  source: 'current_message' | 'history' | 'branch_copy' | 'replay'
}
```

该 manifest 必须：

- 由宿主根据数据库和磁盘生成；
- 不接受模型自行构造；
- 在 Run 开始前校验；
- 注入主助手输入；
- 自动注入所有需要处理文件的协作助手；
- 同时包含图片和文档；
- 在 supplement、queue、steer、Retry、分支和回放中保持一致；
- 不包含已删除、跨 conversation 或校验失败的附件。

主助手和协作助手看到的提示应包含：

```text
<input_files>
- name: resume.pdf
  path: attachments/resume-a13f6c21.pdf
  mime: application/pdf
  source_message: <message-id>
</input_files>
```

并明确：

- 路径相对于当前 workspace；
- 直接读取给定路径；
- 不按原始文件名猜测；
- 多个候选文件时依据 manifest 或向用户确认；
- 文件缺失时报告，不编造内容。

### `list_input_files`

为主助手和允许读取用户文件的协作助手提供只读工具：

```text
list_input_files
```

支持按以下条件过滤：

- 文件名关键词；
- MIME 类型；
- 来源消息；
- 当前轮 / 历史文件。

返回精确相对路径和来源，不返回文件正文。它只用于发现文件，不替代 `Read` 或文档解析 Skill。

### 委派时自动传递

创建专家任务时，宿主根据专家角色和任务自动附加当前 manifest：

```text
<delegated_input_files>
...
</delegated_input_files>
```

主助手仍可以在任务中说明“重点处理 resume.pdf”，但不能承担传递真实路径的责任。

对于资料研究类专家，如果任务不涉及用户文件，可以传空 manifest。对于文书写作和文书审校，存在输入附件时必须传入清单。

## 附件改造优先级

### P0：阻止找不到或读错文件

- 新增统一 `InputFileManifest`；
- Run 开始前校验附件所属 conversation、路径和磁盘存在性；
- 主助手和协作助手自动注入精确路径；
- 图片同时内嵌并列入 manifest；
- 修复 supplement 跨 conversation 附件元数据问题；
- 缺失文件转换为用户可理解的前置错误。

### P1：完善历史、分支和回放

- 新增 `list_input_files`；
- 支持按来源消息定位历史附件；
- 多候选版本时请求用户选择；
- 新对话分支复制附件文件并重建附件记录；
- 回放快照冻结并恢复附件 manifest；
- UI 标明当前引用的是哪个文件版本。

### P2：可观测性与维护

- 记录附件校验失败原因；
- 提供损坏或缺失附件诊断；
- 对旧工作区执行非破坏性一致性检查；
- 统计专家文件读取失败率和用户重新上传率；
- 为未来大文件、云盘引用和外部文件连接器保留适配边界。

## 分阶段实施计划

### 阶段一：删除当前伪 Mailbox

修改内容：

- 移除 `mailbox_post`、`mailbox_reply`；
- 删除相关运行时提示；
- 停止注入 `AgentMailbox`；
- 网页移除 `MailboxThread`；
- 飞书移除“专家往来”摘要；
- API 和公共类型移除 conversation-level `mailbox`；
- 删除“代理信件”活动映射；
- 更新测试和文档。

数据策略：

- 暂时保留旧数据库中的 `agent_mailbox` 表；
- 停止读写；
- 后续数据库版本迁移时再清理。

验收：

- 模型看不到 Mailbox 工具；
- 网页和飞书没有伪信件；
- 原有真实专家委派仍然工作。

### 阶段二：新增协作任务持久化

新增：

- `CollaborationStore`；
- `collaboration_tasks`；
- `collaboration_handoffs`；
- 公共 DTO；
- 任务生命周期测试。

验收：

- 每个专家执行都有 queued、running 和终态；
- 任务绑定 run 和 assistant message；
- 服务重启后仍可读取已完成记录。

### 阶段三：接入真实专家执行

将现有 `createDelegationServer` 接入任务状态：

- 调用前创建任务；
- 执行时更新 running；
- 成功保存结果；
- 失败保存错误摘要；
- 用户停止时标记 interrupted。

同时接入统一附件 manifest：

- Run 开始前校验本轮附件；
- 主助手提示包含所有输入文件的精确路径；
- 专家任务自动附带相关输入文件；
- 图片既内嵌又保留路径；
- 文件缺失时在委派前失败，不让专家猜测。

新增 `submit_specialist_result`。

验收：

- 专家真实执行与数据库状态一致；
- 主助手获得结构化结果；
- 非结构化结果有安全 fallback。

### 阶段四：实现真实交接与 follow-up

扩展专家委派输入，支持 `sourceTaskId`。

验收场景：

```text
项目研究员完成
  → 主助手发起资料核验
  → 资料核验员收到研究员结果
  → 资料核验员真实执行
  → 主助手收到两次结果
```

同时验证：

- 跨 run 的 `sourceTaskId` 被拒绝；
- 失败交接有终态；
- 不允许专家嵌套委派；
- 不存在仅写日志、不运行目标专家的交接。

附件要求：

- follow-up 默认继承源任务使用的附件 manifest；
- 目标专家能看到源专家引用的文件版本；
- 源文件已经缺失时交接失败并标明原因；
- 不允许通过 `sourceTaskId` 引用其他 conversation 的附件。

### 阶段五：绑定 Agent 回复并完成网页呈现

- API 把协作记录绑定到 `MessageDto`；
- 新增回复下方的折叠面板；
- 显示任务、结论、来源、冲突和交接；
- 删除 conversation 顶部的旧信件区域。

验收：

- 当前回答只显示当前 run 的协作；
- Retry 和编辑分支互不污染；
- 没有协作时不显示空模块。

### 阶段六：完成飞书呈现

- 运行中继续更新专家活动；
- 成稿只显示协作摘要；
- 冲突或未确认项才显示提醒；
- 详细记录跳转网页查看。

验收：

- 飞书不会被专家过程刷屏；
- 不显示内部信件全文；
- 摘要与网页结构化记录一致。

### 阶段七：清理与文档收口

- 删除不再使用的 Mailbox 源码和测试；
- 更新 README、飞书说明和架构说明；
- 说明 A2A-ready 边界；
- 确认旧数据库兼容策略；
- 完成全量验证。

## 测试计划

### 单元测试

- 协作任务生命周期；
- handoff 生命周期；
- 非法 specialist id；
- 跨 run 的源任务；
- 结果字段长度；
- 来源 URL 规范化；
- 敏感内容过滤；
- 中断和失败状态；
- 非结构化结果 fallback。
- 附件 manifest 只包含当前 conversation 的有效文件；
- 图片和文档都保留精确相对路径；
- 重名文件保持原始名称与唯一存储路径映射；
- 缺失文件、目录、越界路径、大小不符和 SHA-256 不符；
- supplement 过滤跨 conversation 附件 ID；
- `list_input_files` 按文件名、MIME 和来源消息过滤；
- 多个历史文件候选不会静默选择错误版本。

### 集成测试

至少覆盖：

1. 单专家完成；
2. 两位专家并行；
3. 研究员到核验员的真实交接；
4. 专家失败；
5. 用户停止整轮任务；
6. Retry 产生新的协作记录；
7. 被替换分支不污染当前回答；
8. 网页记录绑定正确的 assistant message；
9. 飞书最终卡片只显示摘要；
10. 不再存在 Mailbox 工具和 UI；
11. 目标专家确实获得源专家结果并产生第二次 Query。
12. 主助手本轮上传 PDF 后获得准确路径；
13. 文书写作和文书审校无需主助手手写路径也能读取附件；
14. 图片既能以内嵌内容查看，也能通过 manifest 定位文件；
15. 后续轮次可以通过 `list_input_files` 定位历史附件；
16. 新对话分支复制文件并创建新的附件记录；
17. 回放恢复与原 Run 相同的输入附件 manifest；
18. 数据库有记录但磁盘文件缺失时，在运行前给出明确错误；
19. 其他 conversation 的附件 ID 不会进入当前 RuntimeInputQueue。

## 安全与隐私要求

- 不保存专家 chain-of-thought；
- 不保存完整原始工具输出；
- 不在飞书暴露本地路径、密钥或内部参数；
- 持久化前对任务摘要和结果摘要做脱敏；
- 对结构化字段设置长度上限；
- 官方来源只保存规范化 URL 和必要元数据；
- 专家失败信息只保存用户可理解的错误摘要；
- 只有与最终答案相关的发现才进入用户可见协作记录。

---

## 非目标

本轮改造不做：

- 通用 Agent 社交网络；
- 专家自由聊天或无限互相委派；
- 每个专家一个飞书机器人；
- 完整 A2A Client / Server；
- Agent Marketplace；
- 跨组织身份和计费；
- 展示完整模型推理；
- 为尚未落地的教育方向提前建设专家体系。

## 最终验收标准

改造完成后必须同时满足：

- 用户看到的每次专家协作都对应真实模型执行；
- 不存在“写了信但专家没收到”；
- 多专家结果确实进入主助手上下文；
- 专家交接有开始、完成、失败或中断状态；
- 协作记录绑定具体 Agent 回复；
- 关键事实可以关联官方来源和核验状态；
- 主助手和协作助手使用同一份经过校验的输入附件 manifest；
- 专家不依赖主助手手工转述文件路径；
- 图片、文档、历史附件、分支副本和回放附件都有明确来源；
- 缺失或损坏文件在模型执行前向用户报告；
- 跨 conversation 附件不能进入当前运行；
- 多个文件版本存在时不允许模型静默猜测目标文件；
- 最终答案始终是用户界面的主体；
- 没有协作时不显示额外模块；
- 飞书不被内部过程刷屏；
- 网页可以展开关键协作与冲突记录；
- 不依赖多飞书机器人；
- 当前不依赖 A2A，但未来可以增加 A2A Gateway；
- TypeScript 类型检查、全部测试和生产构建通过。

完成这些条件后，“专家协作”才从展示性功能变成可信的申学辅助能力。
